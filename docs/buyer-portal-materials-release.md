# Кабинет покупателя — планы, 360° и оригиналы документов (этап 5)

Статус: draft, production не обновлялся. Этапы 1–4 описаны в остальных buyer-portal отчётах.

## Реализовано

- В кабинете отдельная вкладка «Планы и документы» (tj/ru), в том числе когда
  финансовый расчёт требует проверки. Используются готовые technical_plan_path и
  furnished_plan_path/image_path планировки своей квартиры, без генерации изображений.
- 360°: только активный тур с entity_type=UNIT и точным unit_id в том же проекте.
  Нет подстановки другого тура квартиры/планировки/здания/проекта. Панорамы и NAVIGATION
  переходы ограничены комнатами своего тура; UNIT/INFO metadata и чужие переходы скрыты.
- Повторно использован существующий PanoramaSphere/OrbitControls. Комнаты загружаются
  по нажатию, старые изображения освобождаются, WebGL имеет локализованный fallback.
- При отсутствии плана, тура или документа показано понятное сообщение, без подмены
  материалом другого объекта.
- Сотрудник с правом изменения своего договора загружает PDF/PNG/JPEG до 12 МБ как DRAFT
  через панель документов в QR-модалке. Доступен просмотр загруженного файла для проверки.
- Руководитель отдельно разрешает показ или отзывает документ. У покупателя только
  PUBLISHED-файлы с совпадающим текущим владельцем договора.
- Сохраняются исходные байты, SHA-256, язык, вид, порядковая версия и отметка
  «Подписанный оригинал». Признак ставит сотрудник, подлинность проверяет руководитель;
  автоматической проверки подписи/генерации подписанных договоров нет.
- Подписанные оригиналы CONTRACT/SCHEDULE имеют приоритет перед неподписанными копиями
  того же вида/языка. Другие виды не теряются. Уже сохранённый оригинал не перезаписывается:
  содержимое и метаданные immutable, новая версия — отдельный файл/запись.

## Данные и безопасность

Миграция `20261113221119_buyer_portal_materials.sql`, созданная CLI:

- buyer_portal_documents с RLS, без доступа anon/authenticated;
- private bucket buyer-documents с ограничением MIME/размера. Если bucket уже public,
  миграция завершается ошибкой, не делает вид, что файлы защищены;
- restrictive Storage policy закрывает buyer-documents для anon/authenticated даже
  при появлении широких permissive policies. Доступ к другим bucket не изменяет;
- invoker RPC регистрации/публикации, атомарная нумерация версий, аудит с actor/document;
- STABLE invoker RPC материалов с проверкой buyer grants/владельца/статуса одним snapshot;
- запрет подмены оригинала и повторного включения REVOKED-файла.

Клиенту возвращается только метаинформация, без storage path, bucket, hash или подписанных
ссылок. `POST /api/buyer-portal/asset` возвращает байты с no-store/nosniff; PDF — attachment.
Проверки доступа и публикации повторяются после чтения файла. Документ сверяется по
размеру и hash. Покупатель не может передать произвольный URL/path/bucket для скачивания.

Изображения берутся только из разрешённого `/layouts/` на configured frontend либо
image/upload своего Cloudinary cloud; редиректы, traversal, посторонние хосты, SVG/HTML
и превышение размера отвергаются. Статические планы уже публичны в каталоге; кабинет
выдаёт только материал своей планировки. Закрытые документы через Cloudinary не идут.
Панорамы читаются только из published bucket panoramas-360, никогда из drafts.

В браузере — локальные blob URL, без токенов в URL. При отказе очищаются ранее
загруженные материалы; при уходе/смене договора освобождаются URL. Уже полученную или
скачанную копию технически нельзя отозвать с устройства; будущие запросы закрываются.

## Изменённые участки

Backend: buyer-portal/materials.service.js, storage.js, repository/instance/router,
deals.router.js, app.js, sectionAccess.js и тесты. Управление покупателем принимает
deals.manage либо contracts.manage, сохраняя обязательные write-grants и назначение.
Публикация/отзыв — дополнительно только ADMIN/DIRECTOR.

Frontend: BuyerMaterials, BuyerPanorama, BuyerDocumentsPanel, buyerBlob, вкладка
BuyerDashboard, QR-модалка и тесты. Общий TourCanvasErrorBoundary получил необязательные
локализованные строки с сохранением прежних значений для существующего просмотра.

## Проверки

- 388 серверных тестов в 33 файлах, 62 интерфейсных теста в 13 файлах успешно.
- SQL исполняется на PGlite: приватность даже при broad Storage policy, anonymous/RLS,
  versioning, immutable оригинал, публикация/отзыв, смена владельца, свой/чужой тур.
- Проверены SSRF/traversal, MIME, SHA-256, отказ после download, неразглашение путей,
  unsigned/signed precedence, права менеджера/руководителя и защищённые binary responses.
- Проверены интерфейсные переходы, blob cleanup, отсутствие автоматической загрузки
  файлов, сообщения об отсутствии, запрет перехода в чужую комнату и staff draft upload.
- Build с VITE_BUYER_PORTAL_ENABLED=true, lint buyer-компонентов, node --check и
  git diff --check проходят. Существующее предупреждение о размере общих chunks остаётся.
- Для WASM/Postgres регрессии выставлен testTimeout=15000/hookTimeout=20000: исходный
  пятисекундный timeout существующего passport-schema теста на нагруженной среде
  оказался недостаточным. Проверки доступа/ожидания не исключались.

Реальных файлов покупателей, SMS или production-миграций не было. Проверка настоящего
Telegram/WebGL на телефоне и независимых PostgreSQL-сессий остаётся до приёмки.
