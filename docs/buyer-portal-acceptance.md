# Кабинет покупателя — итог автоматической приёмки, этап 8

Дата: 14.11.2026. Статус: DRAFT, production не включён. Это отчёт о проверках, а не подтверждение полной готовности к публикации.

## Исправления по проверке

1. Подтверждение OTP теперь получает advisory-lock покупателя/Telegram **до** блокировки строки OTP. Это убирает потенциальный цикл «confirm держит OTP и ждёт advisory / resend держит advisory и ждёт OTP». Срок, 5 попыток, HMAC и однократность сохранены. Изменение оформлено седьмой миграцией `20261114074913_buyer_portal_acceptance_fixes.sql`.
2. Выбор языка сохраняется и для покупателя, у которого остались только архивные договоры.
3. Активность фиксируется при открытии списка своих договоров; запись ограничена одним обновлением за две минуты и требует действующего либо архивного права.
4. В окне доступа добавлен журнал уведомлений с адресатом «основной покупатель/участник» и состояниями SENT/FAILED/UNKNOWN и др. UNKNOWN не подменяется успехом. Telegram ID, телефоны и тексты чужих сообщений не выдаются.
5. QR доступен из карточки клиента у договора с **точным** совпадением lead_id. Совпадение имени/телефона не подключает чужой договор. Серверная проверка прав сохраняется независимо от UI.

## Сквозной тест приложения

`acceptance-flow.test.js` запускает Express с настоящими buyer-сервисами, проекцией, коммуникационным repository и всем комплектом миграций в PGlite. Адаптер данных исполняет реальные SQL/RPC на синтетических CRM-строках. Только SMS, Telegram и файловое хранилище — изолированные тестовые транспорты; никаких настоящих отправок.

Проверяется цепочка:

- Выдача QR сотруднику → подпись Telegram → SMS на телефон именно из CRM.
- Отказ без подписи, отказ чужому Telegram, одноразовое подтверждение.
- Свой список договоров и реальный расчёт оплат; чужой договор недоступен, служебные поля не выдаются.
- Неопубликованный документ закрыт, разрешённый оригинал выдаётся только своему покупателю.
- Повтор одного обращения создаёт одну задачу CRM; ответ виден в истории.
- Уведомление о принятом платеже содержит правильные суммы и язык; журнал отражает отправку.
- После расторжения доступен архив без текущего долга/графика, язык сохраняется; отзыв документа закрывает его и в архиве.

## Реальная тестовая PostgreSQL

Использован только проект `tozon-crm-commercial-test`, PostgreSQL 17.11. Production-проект не изменялся. Скрипт `scripts/buyer_acceptance_prepare.js` создаёт reviewable SQL с изолированными именами схем; сетевых подключений или отправок сам скрипт не делает. Все зависимости — синтетические, существующие таблицы CRM и настоящий Storage не меняются.

В отдельных схемах исполнены первые шесть миграций и scoped-исправление порядка OTP-lock из седьмой. Результаты отдельных соединений:

| Проверка | Наблюдение |
|---|---|
| 8 клиентских запросов захвата очереди | 8 разных backend PID, 8 разных notice ID, каждая попытка №1 |
| 8 подтверждений одного challenge | 1 VERIFIED, 7 UNAVAILABLE, 1 действующий grant |
| Права функций/таблиц | Проверены локальным каталогом/тестами; публичных SECURITY DEFINER в scoped-наборе нет |
| Очистка | Все 3 созданные схемы удалены; повторный запрос показал 0 оставшихся |

Это многоклиентская проверка однократности, **не** нагрузочный benchmark и не доказательство всех возможных interleaving. Контрольный барьер для одновременного resend/confirm через MCP не удалось надёжно наблюдать, поэтому воспроизведение deadlock и успешный стресс-тест этой гонки не заявляются. Порядок блокировок исправлен по анализу кода; соответствующие SQL/HTTP-регрессии проходят.

Финальная дополнительная попытка dry-run всего актуального комплекта седьмой миграции (включая новые touch/staff_notices) не выполнилась: истёк запрос подтверждения `execute_sql`. За успешный прогон PostgreSQL она не засчитывается. Эти новые функции проверены в PGlite сквозным тестом. Повторная проверка подтвердила отсутствие временных схем; обход подтверждения не выполнялся.

Supabase Advisor проверен на тестовом проекте. Для 10 scoped buyer-таблиц отмечен INFO `RLS Enabled No Policy`: это намеренный deny-all для anon/authenticated, у которых дополнительно отозваны права; серверная service_role имеет свой доступ. Разрешающие клиентские политики ради устранения INFO не добавлялись. [Описание проверки Advisor](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy). Остальные находки тестового проекта были вне этого изменения. После удаления fixtures соответствующие scoped-таблицы больше не существуют.

## Матрица приёмки по ТЗ

| Требование | Автоматическая проверка | Реальная приёмка |
|---|---|---|
| QR из договора и карточки клиента | API/RTL, права и opaque-токен | Телефон/сканирование QR ещё не проверены |
| Telegram + SMS и правильная привязка | HMAC, OTP, лимиты, конфликт/отзыв; сквозной HTTP/SQL | Доставка SMS и Telegram Mini App ещё не проверены |
| Только свои договоры/участники | IDOR, owner/phone/grant/participant, несколько договоров | Два реальных тестовых аккаунта ещё нужны |
| Оплаты, возвраты, бартер, валюты | SQL и проекция, FIFO, исправления/переносы/аннулирование | Сверка выбранных тестовых договоров бухгалтером ещё нужна |
| График/месяц/задолженность | FIFO, первая дата, частичные оплаты, неизвестные сроки | Проверка на телефоне ещё нужна |
| 2D/3D/свой 360° | SQL-изоляция, MIME/URL/hash, отсутствие чужих переходов, RTL | Настоящий WebGL/жесты/масштабирование ещё не проверены |
| Подписанные оригиналы | Immutable, одобрение, защищённые байты, отзыв, архив | Просмотр реального тестового файла ещё нужен |
| Уведомления | Очередь, source/access recheck, суммы, настройки, UNKNOWN/429, несколько клиентов | Настоящая доставка и работа нескольких серверов ещё нужны |
| TJ/RU | UI/API и сохранение в архивном режиме | Чтение текстов и раскладка на телефоне ещё нужны |
| Обращения менеджеру | CRM-задача, idempotency, ответ/история, назначение | Проверка рабочего процесса менеджером ещё нужна |
| Архив после расторжения | Снимок/возврат/отзыв, без будущих данных и текущего долга | Сверка тестового расторжения ещё нужна |
| Действующий бот/РКО/паспорт не нарушены | Целевая регрессия соответствующих модулей | Замеры задержек на действующей инфраструктуре не выполнялись |

330 целевых серверных тестов в 31 файле и 66 интерфейсных тестов в 16 файлах успешны. Build с VITE_BUYER_PORTAL_ENABLED=true, Node syntax и diff --check успешны. Новые buyer-компоненты lint проходят; в существующем ClientDetailModal остаются прежние предупреждения о неиспользуемых imports/hooks, в build — прежнее предупреждение о размере chunks. Общий полный набор тестов CRM не объявляется прошедшим: ранее выявленные ошибки вне buyer-модуля описаны в этапе 6.

## Следующий конкретный этап

Нужен изолированный staging backend/frontend с **отдельным тестовым Telegram-ботом** и согласованным номером для SMS. Нельзя направлять webhook работающего финансового бота на тестовый backend: один бот обслуживает один webhook. Настоящий токен устанавливается через секреты окружения, не в код/отчёт/чат. В staging сначала весь комплект 7 buyer-миграций и совместимый код, затем buyer-флаги. Уведомления включаются отдельно и только для тестовых получателей.

Телефонная проверка: менеджер выдаёт QR тестового договора → два аккаунта проходят вход → сверяются суммы → открываются 2D/3D/360° и оригинал → проводится тестовая оплата → проверяется одно уведомление → отключение/отзыв блокируют доступ → тестовое расторжение даёт только архив. Нужны замеры времени ответа/очереди при нескольких менеджерах. До этого нельзя считать все критерии ТЗ выполненными или включать production.
