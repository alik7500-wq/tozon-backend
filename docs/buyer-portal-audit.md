Проверены названия и поля основных таблиц действующей БД read-only. Полного аудита всех

`identity_documents` — паспортные документы, а не каталог опубликованных покупателю договоров.

## Критические вопросы расчётов

`getDealById` суммирует `amount_minor` у платежей с любым статусом кроме VOIDED.
FIFO, напротив, включает только ACTIVE/POSTED. Оба расчёта суммируют без конвертации внутри
этого кода. Это расхождение критериев, а не доказательство ошибки существующих сумм:
необходимо проследить все пути записи и валютные снимки платежей.

Перед выдачей финансов покупателю обязательны сценарии: TJS/USD, сохранённый курс,
первоначальный взнос, аванс, частичная оплата, бартер, возврат, аннулирование, перенос
между договорами, расторжение и первый срок платежа в будущем. Нельзя пересчитывать
прошлые платежи по сегодняшнему курсу или включать внутрикассовые переводы как оплату.

## Модель новых данных (предложение, не применена)

- buyer identities/bindings: Telegram ID, подтверждённый lead, язык tj/ru, дата проверки,
  отзыв и активность. Один Telegram не получает чужие договоры по одному телефону.
- contract grants/participants: явное разрешение lead → deal, источник и проверивший
  сотрудник; несколько участников; повторная проверка владельца/состояния договора.
- invites: только hash случайного токена, создатель, привязанный договор и участник,
  срок, дата использования/отзыва. Одноразовое атомарное погашение.
- OTP challenges: HMAC кода с серверным секретом, привязка к invite+Telegram+телефону,
  TTL, лимит попыток/повторов, атомарное подтверждение. Без исходного кода в логах.
- published documents: отдельное одобрение для покупателя, приватный путь, версия,
  признак подписанного оригинала; оригинал имеет приоритет перед генерацией.
- notification outbox/preferences: уникальный ключ события, язык, повторные попытки,
  отключение, повторная проверка разрешений и актуальности события перед отправкой.
- inquiries/audit: договор, проверенный покупатель, действие/результат; без OTP и токенов.

Все новые таблицы: RLS включена, без доступа anon/authenticated; доступ через сервер.
SECURITY DEFINER при необходимости — ограниченный search_path, REVOKE EXECUTE PUBLIC,
отдельный тест прав. При отсутствии телефона подтверждение сотрудником с аудитом,
без обхода проверки через произвольный введённый покупателем номер.

## Выполненный код

`telegram-auth.js`: серверная HMAC-проверка Telegram initData, срок 5 минут,
проверка дубликатов полей, постоянное время сравнения, допустимый пользователь;
выход содержит только Telegram identity и не предоставляет доступа к договорам.
QR-токен: 32 случайных байта, base64url, SHA-256 для хранения; укладывается в start payload.
Это вспомогательный модуль: API, погашение токена и SMS ещё не подключены.
Источник алгоритма: https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app
