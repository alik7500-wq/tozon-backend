# Этап 4: проектные формы и атомарное подписание

## Результат

В `/project-workspace` добавлены формы пяти операций: черновик, подписание, ПКО, РКО и складской документ. Действия определяются сервером по актуальным разрешениям пользователя. Все варианты выбора загружаются из справочников своего проекта с пагинацией; ручного ввода технических ID нет.

Новая миграция `20261110153900_company_project_signing_and_options.sql` применяется после этапов 1–3. Она добавляет отдельное право `contracts.sign`, команду `SIGN_DEAL` и RPC `company_project_operation_options`. Старые команды продолжают использовать проверенный алгоритм через закрытую базовую функцию. Обе функции недоступны anon/authenticated.

## Подписание

- Только собственный проектный черновик, действующий клиент и зарезервированное помещение. Чужие ID, смена принадлежности, архив и конкурирующие договоры отклоняются.
- Цена рассчитывается на сервере из текущей квартиры и точного условия схемы. Два оффера с одинаковым взносом, но разной ценой/сроком не объединяются: ключ включает взнос, цену за м², скидку и срок.
- Версии черновика и схемы проверяются. Дата действия схемы учитывает Asia/Dushanbe. Общий предел скидки также проверяется сервером.
- Срок допускает сокращение относительно выбранного оффера; взнос должен достигать минимума. Полная оплата требует срок 0. Без схемы действует базовая цена; для нежилого помещения допустима его ручная стоимость.
- Остаток распределяется по графику целыми центами, сумма строк равна остатку договора. Даты привязаны к исходной дате платежа, без накопления февральского смещения.
- При взносе 0 первая дата по умолчанию равна дате договора; иначе — месяц спустя. Менеджер может задать дату не раньше договора.
- Договор, график, статусы квартиры/клиента, снимок директора на момент подписания и история команды сохраняются одной транзакцией. Отсутствующие ФИО директора или основание полномочий запрещают подписание. Последующее изменение директора не переписывает подписанный договор.
- Плановый взнос не является поступлением денег: фактическая оплата оформляется отдельным ПКО.

## Интерфейс и повтор запроса

Формы показывают свою кассу, склады, клиентов, договоры, ЖК и поставщиков. Наименования материалов — общий справочник без остатков и цен чужих проектов. Выбор другого проекта, выход и фоновое обновление каталога блокируются на время открытой формы. Ответы устаревших запросов игнорируются.

Каждая операция получает UUID. При потере ответа форма сохраняет тот же UUID и неизменное тело, блокирует редактирование и предлагает безопасный повтор. Пока результат не подтверждён, закрытие формы недоступно, при перезагрузке браузер предупреждает о незавершённой операции. После явного отказа сервера (4xx) данные можно исправить. UUID хранится в памяти формы: принудительное закрытие/перезагрузка с игнорированием предупреждения требует проверки результата перед повторным ручным проведением.

## Проверка

- 112 серверных тестов и 17 UI/клиентских тестов прошли.
- SQL-тесты проверяют точные офферы 36/40 месяцев, полную оплату, неизменность снимка директора, устаревшие версии, права подписи, лимит скидки, архив клиента, чужие записи и полный откат при ошибке последней записи.
- UI-тесты проверяют пагинацию, валютный запрос TJS, разные офферы одного процента, чужие справочники, повтор без дубликатов, блокировку формы/переключения и исправление после отказа.
- Сборка Vite и проверка oxlint проходят. Сохраняется существующее предупреждение сборки о крупных общих JS-пакетах CRM.
- Реальная изолированная БД: `scripts/company_workspace_write_smoke_test.sql` выполняет 18 успешных команд для двух проектов с точным подписанием разных офферов, графиками, ПКО USD/TJS, действующим FIFO, РКО, расчётами с поставщиком и складом. Все строки затем ROLLBACK; исходные контрольные суммы projects/users/deals совпали, пилотные пользователи/доступы/команды и денежные движения пусты.
- Миграция применена только на `yaolkwbnhnacxxjpgiyu`. Рабочая БД и main не изменены; постоянные права не выдавались. Проверка безопасности после миграции не выявила WARN/ERROR, остались информационные уведомления о намеренно закрытых RLS-таблицах.

## Граница готовности

Это проверенный код пилота, не объявление полной production-изоляции. Для запуска нужны назначения сотрудников и достоверные реквизиты директоров. Ещё требуются защищённая печать/файлы, отмена подписания и корректировки, фоновые интеграции, разбор старого смешанного учёта, перенос данных и проверка ролей на рабочем сценарии. Прибыль и выплаты партнёрам в этом этапе не реализованы. Флаги пилота по умолчанию выключены и запрещены вне тестового URL Supabase.
