# Этап 5: защищённые документы, печать и вложения

## Что добавлено

В таблице договоров проектного пространства появилась кнопка «Документы». Окно показывает канонические сведения своего договора и директора на момент подписания, позволяет открыть печатную учётную карточку, скачать договор/график Word из действующего бланка и работать с защищёнными вложениями PDF/JPEG/PNG.

Права выдаются отдельно:

| Разрешение | Назначение |
|---|---|
| sections: documents.print + deals.view | Реквизиты своего проектного договора, паспортные данные для бланка, печатная карточка и скачивание вложений |
| дополнительно finance.payments | График и фактические финансовые итоги |
| write_sections: documents.manage | Загрузка вложений к своему проектному договору |

Существующим пользователям новые права не добавляются. Документы разрешены только для договоров с явным company_project_id и действующими собственными связями квартиры/клиента. Старые непривязанные договоры сначала требуют проверки и миграции.

## Печать

- `GET /api/project-workspace/:project/documents/:deal` возвращает явную проекцию своих реквизитов. Обычный просмотр договора по-прежнему не раскрывает паспортные поля.
- `/preview` отдаёт экранированную HTML-карточку с CSP без скриптов, внешних ресурсов и форм. В интерфейсе используется отдельный iframe с ограничениями; печатается только карточка, а не общий экран CRM.
- `/word/:kind/:language` принимает только CONTRACT/SCHEDULE и RU/TJ/UZ/EN. Контекст и ID бланка из браузера запрещены. Сервер выбирает действующий бланк своего ЖК, затем явно общий scope `*`. Бланки другого ЖК не рассматриваются.
- Полный текст договора формируется только из действующего бланка, не из придуманного шаблонного текста. Если бланка нет — явная ошибка. Печатная карточка помечена как учётные сведения, не как полный договор.
- Для Word нужен SIGNED и сохранённые компания/директор/основание полномочий. CONTRACT-бланк обязан использовать `{company_name}`, `{director_name}`, `{director_authority}`. Новая переменная authority доступна в общем редакторе бланков и примерах.
- Имя директора из общих настроек не подменяет снимок подписанного договора. Сумма оплат в печати считается в USD по историческому эквиваленту/курсу, как действующий FIFO. Чужая касса или неопределённая валюта требуют разбора, а не тихого пересчёта. Без доступа к платежам финансовые значения не выдаются; бланк, требующий их, отклоняется.
- После рендеринга доступ проверяется ещё раз. Изменение глобальных реквизитов/действующего текста бланка пока влияет на будущую повторную печать: архивирование конкретной версии готового документа ещё не реализовано.

## Вложения

Миграция `20261110160426_company_project_documents_private_files.sql` создаёт закрытый RLS-реестр company_project_files, RPC проверки/регистрации и restrictive-политику storage.objects для bucket `company-project-private`. Политика запрещает browser-ролям доступ даже при наличии чужой общей permissive-политики. service_role доступен только серверу.

Сам bucket создаётся через Storage SDK при первой разрешённой загрузке: private, до 10 МБ, PDF/JPEG/PNG. Существующий bucket проверяется при каждой операции; если он public, выдача прекращается. Система не создаёт публичные или подписанные ссылки. Старые публичные вложения не переносятся автоматически.

Путь строится сервером: company_project_id/deal_id/UUID загрузки. Имя пользователя в пути не используется. Расширение сверяется с сигнатурой содержимого; SVG/HTML/исполняемые вложения запрещены. Проверяются размер и SHA-256. Скачивание всегда attachment + nosniff + sandbox + no-store, после новой проверки прав. Это проверка формата/целостности, не антивирусная экспертиза PDF.

Загрузка требует UUID в X-Request-ID. Повтор сверяет файл и метаданные; upsert запрещён. После неопределённого ответа регистрации объект не удаляется, потому что транзакция могла уже завершиться. Повтор с тем же ключом находит объект, проверяет байты и завершает регистрацию. Непривязанные объекты остаются закрытыми; для длительного использования понадобится регламент их сверки/очистки. Удаление вложений этим этапом не включается.

Cookie-запросы с Origin принимаются только от FRONTEND_ORIGIN, включая GET: общий permissive CORS приложения не должен давать постороннему сайту читать проектные данные. Для загрузки Origin обязателен при cookie-аутентификации; поддельный Bearer не обходит проверку.

## Флаги и границы

Backend: PROJECT_WORKSPACE_ENABLED, PROJECT_WORKSPACE_DOCUMENTS_ENABLED; для загрузки дополнительно PROJECT_WORKSPACE_WRITES_ENABLED и PROJECT_WORKSPACE_FILES_ENABLED. Все новые возможности по умолчанию закрыты и остаются ограничены точным URL изолированной тестовой БД.

Миграция применена только к yaolkwbnhnacxxjpgiyu. Production/main/рабочие сервисы не изменены, постоянных назначений нет.

## Проверка

- 147 серверных тестов прошли: SQL-права/привязки/RLS, разные проекты, отдельный доступ к паспортным реквизитам и графикам, исторический TJS, отозванные права, неизменность директора, служебные RPC, бланки, XSS/CSP, целостность файлов, повтор загрузки и Origin. Тесты существующих команд и прав также проходят.
- 22 UI/клиентских теста прошли: своя карточка, доступность языков/бланков, поздние ответы другого проекта, повтор одного файла/UUID, блокировка повторного клика/закрытия и запрет печати после отказа доступа. oxlint и сборка Vite проходят; существующее предупреждение о крупных общих JS-пакетах остаётся.
- Реальный SQL smoke в изолированной БД: два проекта, 18 финансовых/складских команд, подписание 36/40 месяцев, документы, исторические итоги, отдельные права и закрытая идемпотентная регистрация метаданных файлов. Всё ROLLBACK; hashes projects/users/deals совпали, финансовые движения/пилотные назначения/файлы/команды/Storage-объекты после проверки пусты. Advisors: нет WARN/ERROR.
- Реальные HTTP-загрузка/скачивание Storage и визуальная печать в настоящем браузере ещё не подтверждены. Storage SDK проверен тестами с подменённым транспортом, SQL-права и регистр проверены на реальной test DB. Для полного end-to-end нужны развёрнутый тестовый сервис, временная учётная запись с явными правами и подходящий Word-бланк.

До production остаются этот end-to-end прогон, отмена/корректировка документов, фоновые интеграции, закрытие/перенос старых файлов и смешанного учёта, назначения реальных пользователей и итоговая проверка ролей. Полная production-изоляция этим этапом не объявляется.
