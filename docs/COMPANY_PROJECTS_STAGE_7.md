# Этап 7: защита от общих фоновых рассылок и выгрузок

## Результат и предел этапа

Новые проектные данные выведены из общих SMS, уведомлений, автоматических задач и финансовых выгрузок Telegram/Google Sheets. Это временный запрет на использование старой общей автоматики, а не готовое подключение SMS и Telegram отдельно для каждого проекта. Назначения проекта не должны автоматически наследовать общий Sender Name TOZON-PLAZA и списки администраторов.

Следующим этапом нужны отдельные правила/получатели/подключения проектов. В этой версии нет переключателя, который разрешал бы обход запрета. Он работает независимо от флага интерфейса пилота: выключение PROJECT_WORKSPACE_ENABLED не возвращает проектные записи в общие отправки.

## Авторитетная проверка источника

Миграция `20261110183023_company_project_background_quarantine.sql` добавляет закрытую для браузерных ролей функцию `company_project_background_blocked(jsonb)`. Она проверяет реальные связи, а не доверяет переданному project_id:

- договор → company_project_id, квартира/ЖК и клиент;
- клиент → явная привязка/интересующий ЖК, в том числе дополнительные телефоны;
- платёж → свой проектный договор или касса;
- строка графика, задача, SMS-запись → исходный договор/клиент/телефон;
- телефон без ID → совпадение нормализованного суффикса с проектным клиентом.

Неизвестные/некорректные переданные ID и неоднозначные данные блокируются. Совпадающий телефон у проектного и старого клиента также блокирует общую отправку: сначала требуется разбор принадлежности. Никакие имена/телефоны/данные других проектов функция браузеру не возвращает; anon/authenticated не имеют EXECUTE.

## Ограничения на уровне БД

| Путь | Поведение |
|---|---|
| sms_events | Проектные события не принимаются в старую очередь; ранее созданное событие не получает PROCESSING после привязки источника к проекту. |
| sms_messages | Проектная запись попытки queued/sending не создаётся/не запускается через общий путь. Существующие результаты отправок и отмены сохраняются. |
| user_notifications | Проектные события не рассылаются общему списку ADMIN. Проектные учётные записи не получают старые общие рассылки, даже если они имеют роль ADMIN. |
| tasks | Старый автоматический путь не создаёт и не меняет проектные задачи и задачи для проектных учётных записей. |

Триггеры возвращают NULL для удержанной вставки/изменения, чтобы фоновая рассылка не ломала исходную транзакцию договора или ПКО. Они не удаляют историю и не переписывают результаты уже состоявшейся доставки. Счётчик старой daily-очереди может отражать попытки, а не фактически созданные удержанные строки; при подключении отдельных проектных очередей метрики нужно разделить.

## Последняя проверка перед транспортом

- SmsService проверяет IDs до формирования отправки и повторно перед провайдером с фактическим телефоном.
- SmsAutoDispatcher проверяет событие до claim и перед вызовом провайдера; подмена/отключение валидатора контекста не снимает отдельную защиту.
- PayomSmsProvider сам проверяет телефон перед любым вызовом своего транспорта, включая тестовый mock-результат. Ошибка проверки принадлежности не разрешает отправку.
- Для Telegram API исходящие методы и для syncSheets добавлена проверка global_export. При наличии проектных назначений/маркеров/привязок/договоров общий финансовый экспорт приостанавливается целиком. Без такого следа обычный старый экспорт работает как раньше. Это намеренная приостановка общей интеграции, а не проектная фильтрация её отчётов.

Напоминания пропускают CANCELLED-строки и проектные договоры; отменённые строки больше не считаются оплаченными в статистике. Проверка SMS-контекста отвергает также исчезнувшую или отменённую строку графика.

## Авторизация планировщика

Общий API-фильтр ранее пытался проверить Bearer-секрет внутреннего SMS-планировщика как CRM JWT. Для одного точного POST /api/internal/sms/payment-reminder/run без CRM-cookie запрос теперь передаётся штатной verifySchedulerToken. Неверный секрет/пользовательский JWT не проходит её. При CRM-cookie проектная граница сохраняется, даже если дополнительно передан настоящий scheduler-секрет. Общего исключения для /internal нет.

## Проверка

- 429 серверных тестов прошли: прежние операции/закрытия/документы, SMS, Telegram и Sheets; новые SQL-проверки источника/очередей/получателей/задач, серверные права функции, отказ транспорта, сохранение обычных старых сценариев и отдельная авторизация scheduler.
- В старых тестах SMS явно задан непроектный результат новой проверки. Для отдельного теста встречи зафиксирована дата, поскольку его историческая дата стала прошлой. Проверки новой границы используют настоящую функцию/отдельные mocks БД и не разрешают вызов внешнего транспорта.
- В настоящей отдельной test DB обновлённый smoke выполняет прежние 28 команд, а также включает фиктивное правило CONTRACT_CREATED только внутри транзакции. Реальный SQL-триггер не создаёт проектные SMS, задачи и общую рассылку; контрольный старый договор создаёт CONFIRM-событие и обычное уведомление. После привязки клиента проекту claim блокируется, отмена события сохраняется. Всё ROLLBACK.
- Payom, Telegram и Google Sheets в проверках не вызывались. Проверки транспорта используют подменённый fetch. Исходные hashes projects/users/deals совпали; пилотные назначения/команды/движения/файлы/SMS/задачи и фиктивные правила пусты после отката. Сохранилось исходное уведомление №1 от 29.10.2026, оно не изменялось. Advisors: только INFO, нет WARN/ERROR.

Миграция применена только в yaolkwbnhnacxxjpgiyu. Production/main/запущенные сервисы и постоянные права не изменены. В интерфейсе этого этапа изменений нет.

## Порядок дальнейшего включения

1. До выкладки кода нужен этот SQL: недоступная функция проверки закрывает исходящую отправку.
2. До назначения рабочих записей проектам остановить общие отправки/выгрузки и проверить незавершённые попытки. Свежая проверка перед HTTP не может отменить уже начавшуюся внешнюю отправку.
3. Реализовать отдельные настройки, очереди, получателей и Sender/учётные данные интеграций для проектов; проверить их на подменах IDs и отключении назначения.
4. Отдельно проверить Instagram/WhatsApp/звонки и агрегатные отчёты: данный этап не заявляет изоляцию всех интеграций CRM.

Также остаются оплаченные расторжения/возвраты и корректировки, настоящий Storage/браузерный прогон печати, перенос старых файлов/смешанного учёта и окончательная проверка реальных ролей. Полная готовность production не заявляется.
