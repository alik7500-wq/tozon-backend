# Кабинет покупателя — QR и вход через Telegram (этап 3)

Статус: подготовлен в feature/buyer-portal; production не обновлялся.
Предыдущие этапы: `buyer-portal-audit.md`, `buyer-portal-auth-release.md`.

## Новое поведение

1. Сотрудник с правом изменения договора открывает «QR-код покупателя» в реестре,
   карточке или окне просмотра подписанного договора. UI показывает ФИО, договор,
   ЖК, объект, QR, срок, скачивание/печать/копирование и состояние Telegram.
2. QR запускает существующий бот с `start=buyer_<random token>`.
3. Buyer-обработчик проверяет срок и состояние приглашения, показывает кнопку
   Mini App. Он не регистрирует покупателя в финансовых подписчиках.
4. Кабинет `/buyer` работает отдельно от AuthProvider CRM, не запрашивает сотрудника,
   не отправляет служебные cookies и не использует служебный JWT.
5. Покупатель выбирает язык (по умолчанию tj), явно запрашивает SMS, вводит код
   в Mini App, получает подтверждение и число явно подключённых договоров.
6. Язык подтверждённого покупателя сохраняется на сервере. В браузере хранится
   только язык; OTP, Telegram initData и QR-токен не записываются приложением в storage.

Доступ к финансовому меню не выдаётся. Сообщения покупателя не получают общую
финансовую кнопку «В главное меню». Одобренные сотрудники сохраняют своё меню.
Обычные команды покупателя с сохранённой привязкой/визитом открывают его кабинет.
Даже при выключенном новом сценарии явный buyer-start не становится заявкой в финансы.

## Защита данных

- QR выдаёт backend; имя бота из getMe. URL Mini App задаёт только сервер.
- BUYER_PORTAL_URL принимает HTTPS, путь /buyer, без credentials/query/hash.
  Ошибка конфигурации останавливает выдачу приглашения.
- В очереди входящих обновлений QR-токен зашифрован AES-256-GCM с отдельным
  доменом ключа от bot token и привязкой к update/chat/sender. Plaintext-токена в
  хранимом text нет; успешные задания по существующей логике очищают payload.
- Визит не создаёт разрешения на договор. Новый RPC visit — invoker, только service_role.
- Секретный hash URL очищается после инициализации Telegram SDK. До этого его
  нельзя удалять: SDK должен прочитать подписанные данные Telegram.
- Код вводится через HTTP API, не через чат с сохраняемой очередью сообщений.
- Привязка, статус и предпочтения проверяют права на сервере. Подмена Telegram ID
  в теле запроса не меняет проверенную личность.

не направлять тестовые сообщения покупателям production.

- Backend: 27 файлов / 275 тестов успешно:
  `npm test -- src/modules/buyer-portal src/modules/telegram-finance src/modules/passport-bridge src/modules/deals`.
- Frontend: 7 файлов / 43 теста успешно: buyer UI/API, QR-права и сценарий SMS,
  существующая печать графика, бартер, приложение 2 и выбор источника продажи.
  Учтён параллельный коммит 602acfc по источнику продажи, ветка frontend перенесена на него.
- `VITE_BUYER_PORTAL_ENABLED=true npm run build`, lint новых компонентов и
  `git diff --check` успешно. Существующее предупреждение сборки о крупных chunks остаётся.
- Тестовая миграция выполнена на PGlite. Production-миграций, реальных SMS и
  production-деплоя не было.
- Настоящий Telegram/WebView и визуальная проверка остаются: локальный запуск
  Chromium заблокирован средой (socket Operation not permitted). JSDOM-тесты не
  заменяют приёмку на телефоне. Также остаётся тест двух PostgreSQL-сессий из этапа 2.

## Что ещё не готово

Это вход и подключение, а не полный личный кабинет. Пока не показываются платежи,
график, задолженность, документы, 2D/3D/360; нет уведомлений и обращений менеджеру.
Основной покупатель поддержан; дополнительные участники договора — следующий этап.
Не сливать draft и не включать production до готовности остальных этапов и приёмки.

Документация Telegram, сверенная при реализации:
https://core.telegram.org/bots/webapps#initializing-mini-apps
https://core.telegram.org/bots/api#inlinekeyboardbutton
