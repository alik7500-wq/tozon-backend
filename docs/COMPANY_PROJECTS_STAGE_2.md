# Проектное рабочее пространство: этап 2, пилот чтения

## Что можно проверять

После подготовки реестра создан отдельный read-only контур `/api/project-workspace`. Он не подменяет существующие финансовые контроллеры и не включает непроверенные операции записи. Пилот программно разрешён только для `yaolkwbnhnacxxjpgiyu.supabase.co`; production запрещён независимо от роли и значения флага.

| Раздел | Отбор данных |
|---|---|
| ЖК | Явная привязка company_project_complexes |
| Помещения | ЖК → корпус → подъезд → этаж → помещение; исключаются архивные элементы |
| Клиенты/лиды | Явная привязка company_project_leads; паспортные данные и файлы не возвращаются |
| Договоры | Принадлежность помещения и клиента одному выбранному проекту |
| Поступления | Своя касса; связанный договор, если указан, также должен быть своим |
| Графики | Только договоры своего проекта |
| Расходы | Своя касса; связанный договор, если указан, также должен быть своим |
| Склады | Явная привязка склада; движения/остатки пока не включены |

В этой версии ограничения проверяются внутри одного server-only RPC `read_company_project_workspace` по аутентифицированному CRM user ID, актуальному состоянию пользователя, пилотному профилю, назначению проекта и отдельным разрешённым разделам. Внешний клиент не может вызвать RPC или прочитать таблицы привязок. Глобальная роль ADMIN не обходит проектные проверки. Данные не выбираются по присланному клиентом actor ID или роли из JWT.

## Общая граница запросов

`workspaceBoundary` монтируется перед CRM API и локальными загрузками. Пользователь с маркером `company.project-only` может обращаться только к GET методам нового пространства, `/api/auth/me`, входу и выходу. Общие списки, поиск, отчёты, экспорт, бланки, все изменения и неизвестные новые маршруты блокируются. Выключение флага не возвращает такому пользователю старый общий доступ. При каждом запросе используется актуальная запись пользователя; отзыв разрешения проверяется в SQL при следующем чтении.

Маркер защищён приватным DB trigger от удаления через старый редактор пользователей, пока пользователь включён в пилотный реестр. SECURITY DEFINER используется только для этой проверки закрытого реестра, не для чтения финансовых данных; функция находится в недоступной клиентам схеме и ничего им не возвращает.

Локальный `/uploads` теперь требует авторизации; проектным пользователям файлы пока полностью закрыты. Уже существующие внешние публичные URL Storage/Cloudinary эта версия не превращает в приватные — отдельная миграция файлов обязательна до production-запуска.

## Запуск только для теста

1. Применить миграции реестра и company_project_read_workspace к изолированному тестовому Supabase.
2. Backend: `PROJECT_WORKSPACE_ENABLED=true`, SUPABASE_URL строго тестового проекта. Для NODE_ENV=test проверяется TEST_SUPABASE_URL. Неверный адрес и выключенный флаг возвращают 503 для проектного пространства, не дают доступ к общим разделам.
3. Пилотные учётные записи получают маркер `company.project-only` и явные подготовительные назначения в company_project_memberships. Затем создаются company_workspace_users и company_workspace_access с enabled=true и минимальным списком sections.
4. Принадлежность клиентов, касс и складов устанавливается только после проверки связей. Миграция сама не назначает пользователей и не относит все данные к Plaza.
5. Frontend после входа направляет такую учётную запись на `/project-workspace`, без общего MainLayout, уведомлений о подписании и фоновых запросов общих разделов. Показываются только разрешённые проекты/вкладки.
6. Проверка доступа обновляется при возврате в окно и каждые 30 секунд. При смене проекта старые строки не отображаются; запоздалый ответ прошлого проекта игнорируется. Ошибка/отзыв доступа очищает показанные данные.

Не создавать постоянные рабочие учётные записи для других объектов на этом этапе. API активации профилей ещё не опубликован, тестовые профили создавались только внутри откатываемой транзакции.

## Проверки 10.11.2026

- 56 серверных тестов реестра, SQL-изоляции, границы API и маршрутов с реальной проверкой JWT.
- 69 существующих тестов матрицы прав, редактирования финансовых разделов и доступа к презентациям.
- 8 тестов интерфейса реестра и рабочего пространства: 50/50, конфликт версии, чужой ЖК, пустое назначение, разрешённые вкладки, запоздалый ответ другого проекта, отзыв доступа, обычный пользователь.
- Сборка frontend успешна, новые компоненты прошли oxlint без замечаний.
- Скрипт `scripts/company_workspace_smoke_test.sql` выполнен на реальном test DB под service_role: два временных ADMIN-пользователя, два ЖК и две отдельные иерархии квартир/клиентов/черновиков договоров/складов. Восемь ресурсов, чужой проект, чужой ID и отзыв доступа проверены. Все fixtures откатились.
- Перед созданием черновиков проверены SMS-триггеры. Договоры создавались только DRAFT; платежи, расходы и отправки SMS не создавались. Существующие суммы и номера не исправлялись.
- После отката company_workspace_users/access и новые привязки пусты; контрольные суммы исходных projects/users/deals совпали. payments/expenses остались пустыми, как до теста.
- Security advisor: только INFO rls_enabled_no_policy для намеренно закрытых server-only таблиц. Новых WARN/ERROR нет.

## Что ещё необходимо до полноценной работы

- Запись: клиент, договор, платёж, расход, перевод, складской документ и подотчёт с атомарной проверкой всех межпроектных связей.
- Проектные остатки касс/складов, себестоимость, партнёрские расчёты и распределение общих расходов.
- Авторизованный доступ к файлам, печати и экспорту; сохранение директора и основания полномочий снимком в договоре.
- Изоляция фоновых задач, интеграций и секретов, уведомлений и сводных отчётов.
- Управляемая активация назначений и аудит изменений доступа.
- Проверяемый перенос существующих данных Plaza/Plaza-2, план отката и production-проверки.

Основные ветки, production база и рабочая CRM этим этапом не менялись. Изолированное чтение проверено, полная операционная изоляция ещё не заявляется.
