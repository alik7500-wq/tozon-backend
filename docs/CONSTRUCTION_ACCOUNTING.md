# Строительный учёт V1

Маршрут: `/finance/construction`. API: `/api/construction`.

## Что реализовано

- Динамические склады, материалы и контрагенты; сотрудник может быть подотчётным лицом и ответственным за склад.
- Начальные остатки на 01.10.2026, поступления, выдача по объекту и виду работ, перемещения, возврат с работ и списание.
- Поступление от поставщика создаёт кредиторскую задолженность. Поступление за счёт подотчётного лица связывается с авансовым отчётом.
- Отдельные виды взаиморасчётов: дебиторская задолженность, кредиторская задолженность, выданные и полученные авансы. Движение за период с начальным и конечным остатком.
- Выдача под отчёт, отчёт, возврат остатка и возмещение перерасхода. Материалы из отчёта повторно не приходуются.
- Сомони и USD отдельно; исходная валюта и необязательный курс сохраняются. Стоимость расхода — средневзвешенная в пределах склада, материала и валюты.
- Черновики можно редактировать и отменять. Авансовый отчёт требует отправки и утверждения конкретным назначенным руководителем.
- Денежная операция ссылается на уже существующий ПКО/РКО целиком: ID, дата, валюта и сумма должны совпадать. Кассовые записи не дублируются.

## Начальная настройка

1. Применить `supabase/migrations/20261012102239_construction_accounting.sql` и затем `supabase/migrations/20261012103959_construction_cash_link_validation.sql` в TOZON CRM. `npm run migrate` не использовать: старый раннер рассчитан на SQLite.
2. Backend использует существующий серверный `SUPABASE_SERVICE_ROLE_KEY`, новые секреты не нужны. Deploy backend и frontend.
3. Открыть «Финансы → Строительный учёт → Справочники и доступ».
4. Выбрать точную учётную запись Акмалхона как утверждающего. Она не определяется автоматически по роли или похожему имени.
5. Создать учётную запись Саидкодира штатным механизмом CRM, если её ещё нет. Назначить только `construction.stock` и `construction.advance`; связать существующее подотчётное лицо «Усмонов Саидкодир» с этой записью.
6. Создать склады и материалы. Единица учёта в V1 одна; закупочные количества предварительно переводятся в неё.
7. Ввести и провести начальные остатки до дальнейших движений по соответствующей позиции/лицу/валюте. Ввод нескольких начальных документов допустим.
8. Внести движение начиная с 01.10.2026 по датам. Связывать только реальные действующие кассовые документы, без перемещений и обменных операций.

## Права и защита

`construction.stock`: все склады и складские документы. `construction.advance`: собственные отчёты/движение, определяется через `construction_parties.user_id`. `construction.settlements`: все взаиморасчёты и подтверждение денежных операций подотчёта. `construction.settings`: справочники, привязка сотрудников и настройка руководителя. ADMIN или явный `*` имеет доступ к модулю; утверждение отчётов всё равно требует совпадения с назначенным руководителем.

Таблицы включают RLS и не доступны anon/authenticated. Запросы идут через API CRM и service_role. Проведение выполняется одной транзакцией с блокировкой настроек; это сериализует операции и исключает гонки остатков. Повторное проведение того же UUID идемпотентно. Прямой RPC закрыт публичным ролям.

Привязанный к проведённому учёту кассовый документ нельзя менять/удалять, иначе долг перестал бы соответствовать кассе. Триггер проверки кассовых ссылок SECURITY DEFINER только читает ссылки и отклоняет изменения, без записи данных; это необходимо для совместимости с прежними кассовыми маршрутами. Его прямой вызов закрыт.

## Границы V1

- Долги покупателей квартир остаются в существующем реестре/план-факте CRM; повторные начальные записи по ним не вводить.
- Нет автоматического распределения оплат по накладным, курсовых разниц или взаимозачётов; денежный документ связывается целиком с одним учётным документом.
- Проведённые документы неизменяемы. Сторно, инвентаризация, возвраты поставщикам, печатные акты сверки, автоматические пересчёты единиц и сметный план-факт — отдельное расширение после запуска V1.
- Подтверждение авансового расхода — ссылка или реквизиты документа в строке; отдельная загрузка вложений пока не добавлена.
- Если материал закупается в двух валютах, его остатки и средние стоимости разделены по валютам. Глобальная пересортировка себестоимости задним числом не выполняется.
- Возврат с работ вводится по документально подтверждённой стоимости, автоматической связи с исходной выдачей в V1 нет.

## Проверки

Backend: `npx vitest run src/modules/construction/__tests__ --fileParallelism=false` — 17 тестов. PGlite запускает настоящий PostgreSQL SQL: атомарность, отсутствие повторной проводки, средняя стоимость, межскладское перемещение, отрицательные остатки, валюта/дата ПКО и РКО, запрет изменения источника, подотчёт/утверждение и недоступность публичным ролям. HTTP-тесты проверяют собственные отчёты и запрет назначения руководителя/проведения чужого отчёта.

Frontend: `npx vitest run src/features/construction/__tests__/ConstructionPage.test.jsx --environment jsdom` — 2 теста; `npm run build`; `npx oxlint src/features/construction/ConstructionPage.jsx`.

Существующие тесты кассы, которые подключаются к реальной БД, не запускались: для них требуется изолированная тестовая Supabase, они создают и удаляют записи.
