# Кабинет покупателя: этап привязки по SMS

Статус: подготовлен backend, выключен по умолчанию. Не является готовым кабинетом.

## Реализовано

- Менеджер с правом изменения своих договоров или руководитель создаёт приглашение
  только для подписанного договора и зарегистрированного в CRM телефона.
- Имя бота берётся из `getMe` действующего финансового бота, а не зашито в ссылку.
- В QR только 256-битный случайный токен, хранится SHA-256. Срок 15 минут задаёт БД.
- SMS отправляется через существующий Payom только на телефон CRM. Клиент не задаёт номер.
- Код: 6 цифр, криптографический генератор, HMAC с серверным секретом, срок 5 минут,
  5 попыток. Повторная SMS не чаще минуты, максимум 5 в час на покупателя и Telegram,
  в том числе при создании новых QR. Предыдущие коды инвалидируются.
- Мок, ошибка или неоднозначный ответ отправки не разрешают подтверждение.
- Погашение QR, проверка кода, создание привязки и разрешения выполняются атомарно.
- Входящие leadId/dealId/telegramId не определяют личность. Каждый запрос требует
  Telegram initData с корректной подписью действующего бота, не старше 5 минут.
- Разрешение выдаётся на конкретный договор. Другие договоры того же покупателя
  требуют отдельного приглашения. Совпадение телефонов не создаёт разрешений.
- Смена покупателя/статуса договора отзывает разрешение навсегда, в том числе при
  обратной смене. Смена телефона отзывает привязку. Перепривязка не происходит молча.
- Руководитель может отключить все привязки покупателя через существующий договор;
  событие сохраняется с ID сотрудника в аудит.
- Новые таблицы с RLS, без прав anon/authenticated; invoker RPC только service_role.
- Из HTTP-логов исключены initData, токен и поле кода.

## Файлы и миграция

`src/modules/buyer-portal/`: Telegram-проверка, repository, service, instance, router,
DB/service/HTTP-тесты. Подключение в `src/app.js` и `deals.router.js`.

Миграция `supabase/migrations/20261113195039_buyer_portal_identity.sql` создана CLI;
проверяется локально через PGlite, к действующей Supabase не применена.
Создаёт invites, bindings, grants, otp, audit и функции проверки/отзыва.
Существующие финансовые записи не изменяет; добавляет триггеры отзыва на сделки/телефон.

## API (пока выключен)

- `POST /api/deals/:id/buyer-invites` — служебная авторизация CRM, ограничение выдачи.
- `POST /api/deals/:id/buyer-unlink` — руководитель с правом изменения, аудит.
- `POST /api/buyer-portal/otp` — body `{token}`, подписанный `X-Telegram-Init-Data`.
- `POST /api/buyer-portal/verify` — body `{challengeId,code}`, тот же Telegram.
- `GET /api/buyer-portal/access` — только явно разрешённые ID, без финансов/паспортов.

Служебный JWT не является авторизацией покупателя. Ответы `Cache-Control: no-store`.
Секретные данные передаются в теле/заголовках, не в query string.

## Конфигурация для последующего тестового запуска

`BUYER_PORTAL_ENABLED=true` включает API только после установки миграции в тестовой БД.
`BUYER_OTP_SECRET` — отдельный случайный секрет минимум 32 байта, не JWT_SECRET,
не bot token. Также нужны существующие TELEGRAM_FINANCE_BOT_TOKEN, Payom и service_role.
Секреты не записывать в репозиторий. Не включать production до готовности всех этапов.

## Ограничения и следующий этап

В этом этапе ещё нет кнопки QR в CRM, buyer-обработчика бота и мобильного интерфейса.
Нет отправки реальных SMS при тестах, production-миграций или production-деплоя.
Дополнительные участники договора пока не получают доступ: этот этап реализует
только основного покупателя. Ручная проверка отсутствующего/некорректного телефона —
обновление CRM уполномоченным сотрудником, затем новое приглашение и SMS, без обхода OTP.

Следующий этап: QR-модалка, отдельный сценарий бота без финансовой регистрации,
мобильный вход tj/ru. После него — проверенная проекция финансов, документов и материалов.
Нельзя принимать SMS-код текстом через текущий webhook бота: его сырые обновления
сохраняются в очереди. Код должен поступать через защищённый HTTP API Mini App.

PGlite проверяет SQL, транзакционные изменения и права ролей. Он использует одно
подключение: тест дублирования проверяет повторное погашение, но не заменяет
нагрузочный тест двух независимых PostgreSQL-сессий перед запуском.
