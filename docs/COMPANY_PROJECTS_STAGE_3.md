# Этап 3: атомарные команды записи в тестовом контуре

## Реализованный серверный интерфейс

`POST /api/project-workspace/:companyProjectId/commands` принимает строго типизированные `request_id` (UUID), `kind` и `payload`. Actor ID определяется из проверенной CRM-сессии. Все записи, расчёты и история команды фиксируются одной SQL-транзакцией.

| Команда | Поведение |
|---|---|
| DEAL_DRAFT | Черновик договора своего проекта; клиент и квартира должны принадлежать ему. Квартира блокируется для повторного оформления. В договоре сохраняются идентификатор проекта и снимок компании/директора/основания полномочий. Подписания нет. |
| PAYMENT | ПКО своего проекта по подписанному USD-договору, оплата USD или TJS по историческому курсу. Используется действующий create_income_payment_atomic и действующее распределение FIFO. Превышение оставшегося долга запрещено. |
| EXPENSE | РКО своей кассы через create_atomic_expense с действующей проверкой остатка. При указании своего контрагента и счёта задолженности — create_expense_with_settlement, без второго денежного движения. |
| STOCK_POST | Поступление, выдача, возврат, списание или перемещение только между собственными складами. Создание документа и construction_post выполняются вместе. Указанный поставщик и ЖК должны принадлежать тому же проекту. |

Доли, учредительские выплаты, межпроектные переводы, бартер, конвертация касс, авансовые отчёты и подписание договора этой версией не включаются.

## Проверки и защита

- Права чтения не дают права записи. На company_workspace_access добавлен отдельный write_sections; значения по умолчанию пустые.
- Разрешения, состояние пользователя и профиль проверяются заново при каждой операции, включая повтор уже выполненного request_id. На время проведения используются блокировки строк.
- Ключ запроса глобально уникален. Повтор того же пользователя/проекта/типа/данных возвращает первоначальный результат; изменение тела или контекста с тем же ключом даёт конфликт. Нельзя повторно начислить кассу, склад или график.
- ПКО/РКО требуют свою активную кассу. Если активные операции уже связывают эту кассу с чужими договорами, проведение блокируется до разбора смешанного учёта. Остаток не считается из скрытых чужих операций.
- Черновик требует свою доступную квартиру и своего клиента; блокировка квартиры и проверка активных договоров предотвращают повторное оформление через новый контур.
- Приватный DB trigger запрещает заменить проект или присоединить чужого клиента/помещение к новому проектному договору через старый сервисный путь.
- Поставщик, склад-источник, склад-получатель и указанный ЖК проверяются до создания складского документа. Недостаток материала откатывает и документ, и движения.
- Операция записи остаётся запрещена на production URL. Дополнительный флаг PROJECT_WORKSPACE_WRITES_ENABLED должен быть явно включён на изолированном тесте.
- Cookie-запросы записи дополнительно требуют точного доверенного Origin из FRONTEND_ORIGIN. Подставленный Bearer-заголовок не обходит эту проверку, если cookie присутствует. Bearer-only вызовы требуют действительного токена.
- RPC, таблицы привязок контрагентов и история команд закрыты для anon/authenticated; приложение имеет только SELECT/INSERT в историю команд.

## Валютный сценарий

На работающей базе существующее FIFO рассчитывает график в USD. Его расчётное тело совпало с изолированной тестовой базой; настройки привилегий намеренно различаются (test invoker, production definer). Расчётные функции не заменялись.

Для тестов сохранён reference snapshot `src/modules/company-projects/fixtures/current_fifo_reference.sql`: это тестовый эталон работающей функции, не миграция. Старый файл миграции 034 не содержит актуальные валютные исправления; подмена работающего алгоритма старой версией не выполнялась.

Проверен пример: 924 TJS / 9,24 = 100 USD. В кассе остаются 924 TJS, в график попадает 100 USD; расход 92,40 TJS сохраняет USD-эквивалент 10. Существующие платежи учитываются с их историческим USD-эквивалентом. Отсутствующий курс/эквивалент старой оплаты требует разбора; новый запрос не должен молча пересчитывать её по сегодняшнему курсу.

Пилот принимает платежи только по USD-договорам с FULL/INSTALLMENT; договоры с другой базовой валютой и бартер требуют отдельной адаптации. Текущая задача не меняет старую финансовую историю.

## Миграции и флаги

Только на `tozon-crm-commercial-test` применены:

1. 20261110085611_company_project_write_commands.sql — отдельные разрешения записи, контрагенты проекта, команды и связи черновика договора.
2. 20261110091429_company_project_payment_fx.sql — согласование новой команды ПКО с фактически работающим USD-FIFO и историческим курсом TJS.

Флаги backend: PROJECT_WORKSPACE_ENABLED=true и PROJECT_WORKSPACE_WRITES_ENABLED=true; URL строго изолированного test Supabase. По умолчанию запись выключена. В интерфейсе текущего пилота пока только просмотр; формы операций будут подключаться отдельно, после проверки подписания и полного рабочего цикла. Постоянные права сотрудникам других объектов не выдавались.

## Результаты проверки

- 154 серверных теста: реестр, граница доступа, SQL-чтение/запись, RPC/маршруты, права существующих разделов. В том числе подмена actor/status, повтор ключа с другим телом, повтор после отзыва права, чужая касса/клиент/контракт/склад/поставщик/ЖК, смешанная касса, недостаток денег/материалов, cookie Origin и валютный график.
- В PGlite используются существующие функции ПКО/FIFO, РКО и складского проведения, а не заглушки положительного ответа. Минимальные schema fixtures приведены к полям, которые реально использует алгоритм.
- На реальной test DB выполнен `scripts/company_workspace_write_smoke_test.sql`: два временных пользователя и два проекта; 14 успешных команд, повторные запросы, ПКО в USD и TJS с частичным графиком, РКО и остаток, погашение поставщику, черновик со снимком директора, склад и откат неуспешных операций. Весь набор затем ROLLBACK.
- Существующие строки test DB не исправлялись. Контрольные суммы старых projects/users/deals проверяются отдельно от добавленных nullable-колонок; payments/expenses, пилотные назначения и команды после теста пусты. Как обычно при проверках вставки, последовательности тестовых ID могут иметь пропуски; рабочие номера production не затронуты.
- Рабочая база, main и запущенная CRM не изменены. Полная операционная изоляция и готовность production не заявляются.
