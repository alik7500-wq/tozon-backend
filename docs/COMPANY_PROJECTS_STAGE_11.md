# Этап 11 — управление доступом и привязками из карточки проекта

## Изменения интерфейса

В карточке проекта добавлен отдельный блок «Доступ сотрудников и привязки». Он загружает сохранённое состояние независимо от редактируемых реквизитов. Пока основная карточка не сохранена, операции настройки недоступны.

- Создание отдельной учётной записи: имя, email, пароль 12–72 байта, проектная роль. Пароль выбирает администратор, не отправляется почтой и не возвращается в ответе. После создания доступ выключен и разрешения пусты.
- Для проектного входа отдельно выбираются чтение и операции, включение/отключение доступа. Общая административная запись не преобразуется в проектную и не теряет права. Название проектной роли само по себе разрешений не выдаёт.
- Создание новой кассы/склада без начального остатка либо закрепление свободной записи без истории. Чужие ресурсы не переназначаются. Ресурсы с денежной/складской историей требуют отдельного переноса.
- Список непривязанных договоров с постраничной выдачей. Кнопка привязки доступна только после явного подтверждения и свежей проверки. В этой версии разрешён только DEMO-001, USD, DRAFT/SIGNED, без закрытия, финансовых записей (включая отменённые), оплаченного графика, бартера и межпроектных связей клиента. Архивная иерархия не ломает весь блок и исключается из простой привязки.
- Привязка меняет только принадлежность договора и клиента; не переписывает цену, график или подписанта. Если у старого SIGNED нет company_director_snapshot, Word остаётся заблокирован до отдельной проверки исторических полномочий. Директор из текущих настроек не подставляется задним числом.
- Пока настройка не подтверждена после сетевого/5xx-сбоя, сохраняются UUID и исходное тело запроса, поля и смена проекта блокируются, есть повтор той же операции и предупреждение перед закрытием вкладки.

Исправлена готовность: условные пункты без назначенных соответствующих возможностей теперь имеют статус NOT_CHECKED / «Ещё не проверено», а не зелёное «Проверено». Это касается связанных прав, касс, складов, бланков и хранилища.

## Сервер и БД

GET /api/company-projects/:id/setup, GET /:id/unbound-deals и POST /:id/setup под прежним company-admin gate, дополнительным точным pilot runtime gate и проверкой Origin для CRM-cookie. Подмена actor, лишние поля, неизвестные права и неподтверждённая привязка отвергаются. Для POST действует ограничение частоты.

Новые RPC — SECURITY INVOKER, только service_role. Актуальный активный администратор с необходимыми settings/users правами повторно проверяется в БД. Общего администратора и собственную управляющую запись нельзя ограничить через SET_ACCESS; нужен уже отмеченный отдельный проектный вход. Нельзя восстановить глобально отключённый профиль, если этим оживут активные назначения других проектов.

company_workspace_access получил отдельную revision. Проектная revision также проверяется на каждой новой команде; создание сотрудника увеличивает её. Новый server-only журнал company_project_admin_commands разрешает SELECT/INSERT, сохраняет автора, проект и результат. UUID блокируется и защищён от повторного использования с другим содержимым/автором/проектом. При повторе проверяется текущая административная авторизация.

Пароли хешируются bcrypt с cost 12 на сервере. В журнал не записывается ни пароль, ни password_hash. Для сравнения намерения при повторе используется HMAC от канонического тела с JWT_SECRET, исключающий различие из-за новой bcrypt-соли. Секрет не раскрывается. users.id в действующей схеме не является sequence, поэтому новые ID выделяются под SHARE ROW EXCLUSIVE блокировкой users, совместимой с настоящими legacy-вставками только последовательно.

Исправлено сохранение реестра: настроенные назначения обновляются без удаления FK-родителя. Удаление назначения с историей доступа и отвязка ЖК с проектными договорами запрещены с понятной ошибкой. История не удаляется ради сохранения директора/долей.

Миграции 20261111180927_company_project_admin_setup.sql и 20261111182317_company_project_setup_archived_preview.sql применены только к yaolkwbnhnacxxjpgiyu. Вторая исключает архивные цепочки из простого списка переноса. Рабочая база не изменялась.

## Проверка

- 178 серверных тестов прошли (проектные модули + отдельный pilot). Дополнительно повторно прошли 7 SQL-проверок после добавления сценария архивной цепочки: права, отдельная запись, зависимые разрешения, конфликт версии, отказ общему администратору, повтор UUID, чужой ресурс/договор, история, сохранение реестра с настроенным FK и запрет удаления связанной истории.
- 40 UI-тестов и сборка пилота прошли; oxlint изменённых компонентов без замечаний. Сохраняется старое предупреждение крупных chunks.
- На реальной test DB scripts/company_project_admin_smoke_test.sql создал отдельную запись, подтвердил повтор без дубля, защиту общего администратора, включение/отзыв прав, кассу/склад и привязку демодоговора с неизменным подписантом/ценой; всё ROLLBACK.
- После SQL smoke users/deals hashes совпали с исходными. Ваши сохранённые реквизиты Plaza и revision=3 не изменились. Постоянных новых учётных записей, доступов или привязок этим тестом не создано. Security advisors: только INFO.

Публикация выполняется только в feature/company-projects-foundation и двух согласованных тестовых сервисах. Blueprint/платные ресурсы/production/main не изменяются. Настоящие права и принадлежность через новый интерфейс выбирает администратор; они не включаются автоматически при выкладке. Полная проверка Storage/Word и перенос рабочего старого учёта остаются отдельными задачами.
