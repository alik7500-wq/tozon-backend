# TOZON CRM — document settings

Administrators can upload DOCX templates for contracts, acts, PKO, RKO, payment schedules, reservations, offers and apartment cards. Templates have a language and an optional project scope. New uploads activate a new revision; historical files remain downloadable and can be restored. Documents are generated from the existing print-view snapshot, including saved exchange rates and FIFO schedule data; generation does not create or update financial records. Staff can generate documents from active templates but cannot upload files, access original templates or edit configuration.

Custom documents download as Word files. Open the generated file in Word to inspect, print or save as PDF. Existing browser print forms remain available. The technical sample demonstrates supported placeholders; it is not an approved legal contract. DOCX files must be at most 2 MB, with at most 12 MB unpacked contents, and cannot contain macros, embedded objects or external relationships. Standard formatting, tables and embedded logos remain supported. Unknown placeholders and raw XML expressions are rejected.

The settings catalogue links existing project, SMS, personnel, payment dictionary, automation, reports and notification sections. New settings cover company details/signatories, builder and branch registries, numbering, maximum discount and default reservation duration. Builder names are selectable when creating projects. Branch names are selectable in document company details. The interface tab stores a browser-specific primary accent and default language of the built-in print forms. This is not a complete Uysot feature clone: KPI compensation formulas, penalty accrual and translation of the entire interface are not implemented.

Configuration changes use optimistic version checks and retain history. Number masks affect inserts only. They require the row ID (`{id}` or `{id4}`), can include the document year, and contracts can additionally include project code, building and unit. PKO/RKO numbers are stored separately from operation references so transfers and conversions keep their original semantics. Previously issued numbers, transactions, cash amounts and historical exchange snapshots are untouched. The numbering trigger is SECURITY DEFINER only in a private, non-exposed schema because legacy inserts use both anonymous and service-role DB clients; it reads only numbering configuration, is not callable by public roles and has a fixed search path. Settings tables have RLS and no anonymous/authenticated privileges. Mutation RPCs are service-role only and check an active ADMIN actor.

Migrations: `src/db/migrations/20261008190907_document_templates.sql` and `20261008192509_document_settings_service_policies.sql`. Initial configuration is empty, so existing numbering and reservation/discount behavior are preserved until an administrator changes settings. Apply migrations before deploying backend. The second migration adds explicit service-role policies without granting anonymous or authenticated access.

Validation: 57 backend tests passed (DOCX engine, actual isolated PostgreSQL migration/numbering/access tests, API authorization tests and existing contract-amendment/FIFO regressions); 10 frontend tests passed (template upload, language/project selection, cents/context preservation, stale settings and contract-amendment regressions). Production frontend build passed. No customer document was changed for testing.
